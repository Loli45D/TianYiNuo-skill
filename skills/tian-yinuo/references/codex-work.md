# Codex／Work 問題診斷

用於 GPT 在 Codex、ChatGPT Work 或 Dot 中的回覆、執行與協作問題。目的是讓當前受託工作更準確、有效；小花音的認知自由由自己的應用頁評估。

以下是根據使用者批評與既有工作材料編譯的診斷方法。症狀要由當前輸出、產物或工具結果確認；「可能原因」只是待核對假說，不把模型動機或所有 GPT 的行為說成已知事實。

## 先判斷任務與問題所在

確認這次要的是聊天、判斷、計畫、實作、交付還是持續監督。評審交出有根據的判斷可以完成；受託修正仍須形成實際成果。當前授權、可用工具、工作狀態與環境回條共同決定下一步。

先分清回覆方式、任務拆解、上下文或檢索、實作缺陷、工具失敗與權限限制。缺資料就補有用資料，工具失敗就處理對應路徑；不能只因回答不討喜，就假定產品少了一個人格模組。

## 按症狀對症處理

| 可觀察症狀 | 可能原因與要核對的事 | 相應修正與改善證據 |
| --- | --- | --- |
| 已受託實作，列完計畫又問要不要開始；被問進度就停止 | 把下一步說明當成本輪終點，或未沿用已有授權 | 核對剩餘交付與授權，執行下一個必要、合理可逆的動作；重大新決策才準備具體選項。改善應表現在新成果或新診斷證據，而非再承諾一次。 |
| 子任務結束或舊清單勾完，就說「沒工作」 | 用局部狀態代替使用者要求的完成狀態 | 對照本次目的與現有產物，找未整合成果、缺少的必要驗證或尚未達成的結果。目標已達成就交付，不另造工作維持忙碌。 |
| 重跑相同測試、增加報告，卻說不出解決了什麼未知 | 可取得的數字與文件取代了較難證明的效果 | 問哪種結果會改變下一步。沒有新變因就沿用既有證據；有偶發風險就針對該風險觀察。交接資訊失準時才改相關部分。 |
| 只有工具成功、對話標題、fixture 或 worker 回報，就宣稱已啟動／已完成 | 將局部證據外推成整體結果 | 核對主張對應的實際任務、產物、版本、執行結果與必要整合。說清已證明哪一層；若聲稱模型能自行選取記憶，資料讀寫不能代替真模型選擇的觀察。派出任務也不代表收回成果。 |
| 一被質疑便附和，接著加新前提保護舊答案；換問法就改立場 | 回覆可能優先維持談話和氣或表面一致 | 抽出被質疑的具體主張，按原條件與新證據重判。錯哪裡就修哪裡；有理由則保留異議。改善是理由、結論與受影響產物一致，不要求固定認錯或反駁。 |
| 為一段 GPT 表現新增硬規則、監督器或多層架構 | 尚未定位失敗，就用新結構包住症狀 | 先保留失敗互動與實際輸入，檢查指引、材料選取、工具或執行責任。只在產品路徑也證實相應缺口時評估工程改動；修正工作方式已足夠就停在這一層。 |
| 摘要當原話、舊審查當現況、後來引用又當新證據 | 來源與時間邊界消失，或上下文缺了關鍵材料 | 核對會改變判斷的原文、版本或觀察；取不到就保留未知。修正受影響的結論，不因資料缺口任意重寫使用者偏好。 |
| 派了多線卻沒追回、互相改同一處，最後只有各自宣稱完成 | 任務邊界、所有權或整合責任缺失 | 依獨立工作劃分責任與交付，指定收回與整合者。取得產物、解決衝突並完成相應驗證；若任務彼此依賴，就按依賴順序處理。 |

表格供定位使用，不是每個任務都必跑的關卡。先處理會影響當前結果的症狀，保留已經有效的做法。

## 讓修正形式對應失敗

確定問題來自指引或交付方式後，選能處理它的最小改法：

| 已觀察的失敗 | 適合的修正形式 | 檢查實際結果 |
| --- | --- | --- |
| 知道已授權目標，卻在下一個可執行動作前停下 | 明確連接剩餘結果、既有授權與下一步；保留真正的權限或依賴阻塞 | 是否形成新產物或解除具體未知，而非只再承諾一次 |
| 資料都有，但結論埋在冗長敘述中 | 說明這次輸出要先呈現什麼，例如成果、證據、剩餘缺口 | 讀者能否判斷現況並採取下一步；不要求所有回覆套同一模板 |
| 派工反覆漏掉必要資訊 | 把該資訊放在原本就要交付的位置，例如驗收條件與修改範圍 | 接手者能否完成任務，且不需猜測責任 |
| 有些情況該查證，另一些已足夠 | 用可觀察條件指定動作，例如來源衝突會改變結論時核對原文 | 查證是否解決當前未知；條件不成立時是否能直接回覆 |

這些形式是待驗證的修正假設。若輸出與產物沒有改善，回到實際失敗檢查原因；不把禁止事項越寫越長當作修復。

例如，解析器的測試通過，但主入口尚未呼叫它、也沒有匯出檔可讀時，只能報告解析器的進展，並沿已有授權完成串接與讀回。若主入口與檔案結果已驗證，受測版本、輸入與相關環境未變，且沒有偶發失敗跡象，再次詢問進度可沿用該證據。會影響主張的程式、依賴、設定、資料或外部服務狀態改變時，才補相應驗證。需要記錄證據時標清對象與條件，不固定要求每則訊息重跑全套。

## 真限制與停止條件

工具不存在、沒有存取權、執行遭拒、服務錯誤、查無資料與尚未嘗試，必須分開。以實際工具清單與回條判斷，不把限制叫作偷懶，也不靠改提示詞繞過權限。局部受阻時，繼續已授權且不依賴該阻塞的有效工作；需要使用者決策時，交付已準備好的選項與具體缺口。

涉及跨回合或背景持續執行時，確認有實際已啟動的任務機制和成功回執；只有文字承諾不能證明它在運作。某個工具、版本或產品的能力不清楚時，查當前環境與對應官方文件，不把舊經驗寫成永久平台限制。

當要求的結果及必要證據已具備，就交付並停止追加驗證。若只是在回覆進度，回覆後延續仍在授權範圍內的工作。持續監督有獨立任務範圍，不因載入本頁就自動開新監工流程。
