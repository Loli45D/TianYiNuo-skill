# 一般工程判斷

用於程式、資料、模組、介面與架構。這裡包含通用軟體設計知識，再以主檔的目的與成本取捨判斷怎樣使用；不把一般工程原則說成田以諾獨有的發明。GPT 的工作行為另見主檔的 Codex／Work 入口。

## 沿著一次變動看設計

選一項當前需求或有明確依據的預期變動，沿輸入、處理、狀態與輸出追蹤：誰擁有規則，誰需要知道內部細節，要改哪些地方，可能破壞什麼承諾。用這條實際路徑判斷結構。

可明確重現的查詢、運算、儲存與執行，優先由程式承擔；需要語境解讀、權衡或自主選擇時，再確定適合的認知責任。兩者以清楚契約銜接，不把每個模糊詞都拆成額外模型呼叫。例如先解讀「上次見面」指哪次事件，再由程式查精確時間區間。

| 判準 | 具體檢查 | 改法與取捨 |
| --- | --- | --- |
| 高內聚、清楚責任 | 一個模組的工作是否圍繞同一概念、規則或共同變動原因？無關需求是否被塞進同一個共用工具？ | 把有共同責任的內容放一起，讓無關變動能分開處理。單一責任不按函式數量或檔案長度切割。 |
| 低耦合、合理依賴 | 改一個內部表示，是否迫使多個無關模組一起改？依賴的是明確契約，還是對方的私有欄位、順序與隱含假設？ | 把易變知識留給擁有它的部分，讓呼叫方依賴穩定契約。依賴數量多不直接等於耦合過高，也不追求零依賴。 |
| 資訊隱藏、介面契約 | 呼叫方為了正確使用，得知道多少內部細節？輸入、輸出、副作用、順序、錯誤與生命週期是否清楚？ | 在正確邊界完成轉換與規則執行。介面可保持簡單，內部承擔必要複雜度。類別與 private 標記本身不能保證封裝。 |
| 抽象與重用 | 重複的是同一業務規則，還是只是程式形狀相似？新增一層究竟隱藏了什麼差異？ | 共用應共同演進的知識；不同變動原因可各自保留。薄 adapter 若隔離真實平台差異就有價值；純透傳層則檢查能否省去。 |
| 可讀性、明確語義 | 命名、單位、時間、空值、來源與狀態能否讓維護者正確預測行為？修改是否需要追蹤大量隱藏副作用？ | 讓概念與責任直接可讀。保留會影響下一步的狀態差別，例如查無資料、服務失敗、格式錯誤與尚未實作。 |
| 正確性與可靠性 | 哪些不變條件不能破壞？重試、併發或部分失敗會造成什麼實際後果？ | 依具體故障保留需要的鎖、逾時、原子性、去重或權限檢查，避免假成功。防護的價值取決於保障的情境。 |
| 可驗證、可演進 | 檢查是否能發現對外承諾被破壞？替換內部實作後，行為不變時測試是否仍成立？ | 驗證可觀察結果、狀態與必要副作用；確有內部性質要求時再檢查它。功能、效能與整合各取足以支持其主張的證據。 |

這些是診斷問題的判準。是否採型別、物件導向、依賴注入、框架或獨立服務，要看它在目前規模中改善了什麼；不把術語或固定層數當成成果。

遇到同名異義，先用具體情境區分概念，再核對現有術語與程式；只有反覆混淆或共同協作需要時，才把已確認的定義補進專案既有術語表。未確認的說法保留為假設。若某個前提會改變方案選擇，指出它由什麼保障，以及哪個可取得的觀察會改變建議；不為每次小判斷另建紀錄表。

## 看具體後果，再決定重構幅度

以下是推演案例，示範成立條件，不能直接當成所有專案的改法。

- **相同形狀，不同責任。** 倉庫缺貨與訂閱流失目前恰好共用十行標籤規則，只有物流一側要加入安全庫存條件。維持共用會把兩種需求綁在一起，適合讓規則各自歸屬；若其中只有純格式處理確實共同演進，可只共用那部分。反過來，報價與結帳若必須遵守同一份折扣資格，就應讓這項規則有共同責任位置。
- **現有結構已足夠。** 三個 route 呼叫純函式、沒有共享可變狀態，已確認的欄位修改也容易完成時，可保留結構。新增分層須指出它要降低哪項實際成本；後來出現多個呼叫者重複處理同一規則時，再重新評估。
- **一種實作仍可能需要邊界。** 寫入模組集中處理原子提交與回滾，即使只有一種資料庫，也在隱藏呼叫者不該各自處理的責任。若查明這些保障已完整由下層持有，而該層只有透傳，才檢查能否移除，並保留原有行為契約。

評估抽象時，假設拿掉它：複雜度會消失，還是回到多個呼叫端？再看它承擔的契約、平台差異、生命週期與有依據的變動。這是定位收益的問題，不以實作數或方法數設定硬門檻。

保留已能服務目的的 route、callback 與模組。當現有結構阻礙正確性、維護或已確認能力時，再做相應重構。先完成能檢驗用途的最小充分實作，保留後續演進空間；有明確依據的前置設計也可以成立。

資料取得與呈現一起設計：常用摘要容易取得，低頻詳情保持可達。快取、預取與延後載入各自比較時效、資源與理解成本，避免因精簡而丟掉必要資訊。

當介面存在會影響後續修改的重要取捨，而且第一個方案不足以判斷時，才提出兩個實質不同的候選；可讓獨立代理使用同一份需求與材料。各給一個呼叫例，說清輸入、結果、失敗行為及隱藏的責任，再比較理解成本與變動範圍並給出建議。小改動或收益已明確時直接處理；不為湊方案增加層數。

## 判斷是否改好了

回到原先那項變動：需要一起修改的無關部分是否減少，責任是否更容易找到，必要契約是否仍成立，新增抽象是否值得其成本。已有足夠證據就結束這項檢查。

依據：Parnas 的模組劃分與資訊隱藏、Microsoft 的高內聚與低耦合指引、Ousterhout 的模組介面與抽象成本，以及 Google 的行為驗證原則。完整來源與適用限制列於主檔連結的「依據與適用範圍」；此頁案例是應用推演。
